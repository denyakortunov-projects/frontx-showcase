# FrontX Event Calendar — первый дизайн-контракт

5 октября 2026 · Предложение для ревью · Локальная спецификация, без реализации и публикации.

**Результат:** переиспользуемая композиция календаря событий для разработчиков FrontX. Один компонент должен работать на отдельной странице, внутри продукта и в компактном блоке. Собственный продукт, сервер и новая библиотека примитивов не нужны.

## 1. Основание и границы

Источник направления — ответы Дениса в текущем чате от 5 октября, после [стартового брифа](../../../../docs/ux/proposals/2026-10-05-frontx-calendar.md). Изначальные вопросы закрыты в следующем объёме:

| Вопрос | Ответ Дениса / принятое ограничение |
| --- | --- |
| 1. Размещение | В существующем FrontX Showcase; можно упростить навигацию. Точный раздел выбираем в предложении ниже. Публикация отдельно не запрошена. |
| 2. Пользователи | Личное и командное планирование, учебные тесты, мероприятия, групповая работа. Потребитель компонента — разработчик продукта. |
| 3. Согласование | Визуальная совместимость с Constructor Fabric и существующим FrontX, включая цветовые схемы. Конкретный календарь платформы и его API не указаны; интеграция не подтверждена. |
| 4. Событие | Название, начало/окончание, часовой пояс, «весь день», описание. |
| 5. Данные | Только синтетические локальные события. Контракт синхронизации сейчас не нужен. |
| 6. Сетка | Рабочие часы при открытии, прокрутка, шаг 30 минут, понедельник. |
| 7. Создание | New event и нажатие на свободный слот. |
| 8. Особые события | Полоса All day, пересечения рядом, видимый часовой пояс. |
| 9. Дополнения | Исследовать стандартные подходы и предложить границы; все функции чужих календарей автоматически не включать. |
| 10. Ревью | Краткая спецификация взаимодействий и состояний Day/Week. Финальный принимающий решение не назван. |

Первый дизайн-результат включает Day, Week и предложенный компактный Agenda, Standard/Compact, просмотр и общую форму создания/редактирования, состояния и проверочные сценарии. Навигация Showcase описана как отдельная небольшая правка. Кликабельная реализация, библиотечный API, срок поставки и одобрение Виталия Пантелеева, Дениса Турановича или Николы этим документом не установлены.

## 2. Что берём из существующих решений

Проверены официальные источники 5 октября 2026. Это анализ документации, а не сравнительное браузерное тестирование или подтверждение популярности по метрикам.

| Источник | Наблюдение | Решение для FrontX |
| --- | --- | --- |
| [shadcn Calendar](https://ui.shadcn.com/docs/components/calendar) | Calendar выбирает дату/диапазон и использует React DayPicker. | Переиспользовать установленный FrontX Calendar для выбора даты. Не превращать date picker в сетку событий и не заменять его экспорт. |
| [FullCalendar TimeGrid](https://fullcalendar.io/docs/timegrid-view) | Одна временная сетка обслуживает день и неделю; отдельно настраиваются полоса All day, высота слотов и перекрытие событий. | Общая TimeGrid для Day/Week, а не две независимо оформленные страницы. Рабочие часы — положение прокрутки, не обрезание данных. |
| [FullCalendar List](https://fullcalendar.io/docs/list-view) | Список показывает события за заданный период и имеет пустое состояние. | Предложить Agenda как компактное представление того же периода и набора событий. |
| [FullCalendar Event Object](https://fullcalendar.io/docs/event-object) | Идентификатор, время, all-day и пользовательские поля разделены; окончание исключающее. | Явно определить временную семантику и отдельное место для расширений продукта. |
| [Schedule-X configuration](https://schedule-x.dev/docs/calendar/configuration) | Раздельно конфигурируются представления, зона, начало недели, шаг сетки, размеры и поведение при сужении. | Разделить view, density и dimensions; не зашивать один экран и одну локаль. |
| [MUI X Scheduler](https://mui.com/x/react-scheduler/) | Отдельная линейка компонентов планирования; на момент чтения помечена beta. Повторения и некоторые возможности данных выделены отдельно. | Форма базового события не обязана сразу включать повторения, ресурсы и серверные сценарии. Material UI как второй набор примитивов не добавлять. |

**Предложение по техническому направлению:** сначала проверить FullCalendar как движок сетки под FrontX-композицией; Schedule-X оставить альтернативой. Это кандидат, не выбранная зависимость. До установки нужны небольшой проверочный пример, проверка лицензии выбранных модулей, совместимости с React 19, переоформления токенами, клавиатуры и часовых поясов. Не писать собственную календарную арифметику, DST и раскладку пересечений без такой проверки. В этой задаче зависимости не меняются.

## 3. Из чего складывается компонент

Рабочее имя **EventCalendar**, чтобы отличать расписание от существующего `Calendar`. Все имена ниже — предложение композиционного контракта, не опубликованные экспорты UI Kit.

| Модуль | Ответственность | Что может заменить потребитель |
| --- | --- | --- |
| EventCalendar | Общее состояние даты, вида, выбранного события и зоны отображения | Управление состоянием снаружи, входные события и callbacks |
| CalendarToolbar | Today, предыдущий/следующий период, выбор даты, Day/Week/Agenda, New event | Внешняя панель навигации; встроенную можно отключить |
| TimeGrid + AllDayLane | Один день или неделя, ось времени, свободные слоты, пересечения | Настройки сетки и формат подписей, не произвольные CSS-переопределения состояний |
| EventItem | Название, время, продолжение на другой день, выбор и фокус | Дополнительная предметная подпись через ограниченный слот |
| Agenda | Те же события списком по дням | Компактное встраивание без временной сетки |
| EventDetails + EventEditor | Просмотр и одна форма для создания/изменения | Добавочные поля/действия продукта через слот; базовая валидация сохраняется |

Компонент получает события и сообщает намерения create/update/delete/select/range-change. Сохранение, права, приглашения и загрузка принадлежат приложению-потребителю. Showcase позже реализует callbacks через локальное состояние. Наличие кнопки Edit не подтверждает право на изменение в реальном продукте.

Не вводить в core типы «тест», «урок», «Gear», «проект» или «команда» как обязательные сущности. Такие примеры отличаются подписью и адаптером данных. Информацию для расширений передавать отдельно от общих полей события; она не исполняет произвольный код из JSON.

## 4. Виды, плотность и размер

| Ось | Варианты | Правило |
| --- | --- | --- |
| Представление | Day / Week / Agenda | Меняет способ показа событий. Week — стартовый вид широкого примера. |
| Плотность | Standard / Compact | Меняет отступы и количество вторичной информации, не набор данных или часовой шаг. |
| Контейнер | Заданная потребителем ширина/высота | Не зависит от размера всего окна и не задаёт отдельную модель событий. |

**Предлагаемые размеры для дизайн-проверки, не принятые breakpoints:** Week 1120×640, Day 640×640, Agenda Compact 360×360. На узком контейнере предлагается Agenda; автоматическое переключение — только при явно выбранной потребителем адаптивной политике. Принудительный Week сохраняет минимально читаемую ширину дней и горизонтальную прокрутку внутри компонента.

Compact сохраняет размер читаемого текста, видимый фокус и доступные цели нажатия. Убирает описание из карточки, сокращает служебные отступы; полное название, время и зона остаются доступны в деталях. Не применять общее `transform: scale()` или текущий графиковый коэффициент высоты 65% к календарю.

В Agenda показывать All day первой группой дня, затем события по времени. Период сохраняется при переходе из Week (семь дней) или Day (один день); переход обратно использует выбранную дату. При нехватке высоты — прокрутка списка; ничего не обрезать без способа открыть оставшиеся события. Панель действий закреплена, содержимое прокручивается.

## 5. Компоновка первых состояний

Подписи интерфейса Showcase — английские. Ниже схемы состава, не пиксельные макеты. Геометрия будет проверена на реальных FrontX-примитивах до принятия визуального результата.

**Week / Standard**

```text
Calendar          [Today] [‹] [›] [5–11 Oct 2026 ▾]  [Day | Week | Agenda] [New event]
Asia/Singapore (UTC+08:00)
          Mon 5       Tue 6       Wed 7       Thu 8       Fri 9       Sat 10      Sun 11
All day   ────────────────── Group workshop ──────────────
08:00     ·           ·           ·           ·           ·           ·           ·
09:00     Planning    ·           ·           ·           ·           ·           ·
09:30     Review | Group work     ·           ·           ·           ·           ·
10:00     ·           Course test ·           ·           ·           ·           ·
          [внутренняя прокрутка полного дня 00:00–24:00]
```

**Day / Compact:** та же панель, одна колонка выбранного дня, одна полоса All day, те же EventItem и редактор. Заголовок и действия могут переноситься на вторую строку; зона не исчезает. В текущем примере первоначальная прокрутка к 08:00, рабочий ориентир 08:00–18:00, без блокировки ранних, вечерних и выходных событий. Это уточнение дизайнера к принятым рабочим часам, а не запрет продукта.

**Agenda / Compact:** заголовок периода и New event; группа даты → All day → строки `09:00–09:30 · Planning`. Никаких миниатюрных семи колонок. Нажатие строки открывает те же детали. Видимый диапазон, количество событий и выбранный event сохраняются.

**Просмотр события:** `Sheet` справа; заголовок события, дата/интервал, часовой пояс, описание при наличии; Edit. На узком экране Sheet занимает доступную ширину. Для удаления предлагается отдельное действие Delete и подтверждение с названием события. «Cancel event» не добавлять: отмена встречи требует жизненного цикла и уведомления участников.

**Создание/редактирование:** один `EventEditor` внутри `Dialog`; Title → All day → Start/End → Timezone → Description; Cancel / Create event либо Save changes. Начальные значения при нажатии слота берутся из него; New event использует выбранную дату и ближайший будущий получасовой слот для сегодняшнего дня, 09:00 для другой даты. Предлагаемая начальная длительность — 30 минут, доступна правке.

## 6. Минимальная модель и поведение времени

Общие поля: стабильный `id`, `title`, необязательное `description`, признак `allDay`. Название обязательно после удаления пробелов по краям.

- Timed: начало/окончание как однозначные моменты времени, IANA `timeZone` события. End строго позже Start. Сетка использует общую зону отображения, подписанную над ней; детали дополнительно показывают исходную зону события и её смещение на дату события.
- All-day: `startDate` и исключающий `endDate` как календарные даты, без фиктивного полуночного UTC. В форме пользователь выбирает включительную последнюю дату; адаптер переводит её в исключающее окончание. Однодневное событие 5 октября хранится как `[2026-10-05, 2026-10-06)`. При смене зоны календаря эти даты не сдвигаются.
- Переключение All day в черновике сохраняет прежние timed-значения для обратного переключения. Пока All day включён, часы и timezone скрыты; случайно введённое время не попадает в сохранённую all-day запись.
- Изменение зоны отображения сохраняет моменты событий. В редакторе изменение timezone по умолчанию сохраняет момент и пересчитывает видимые часы; последующее изменение часов меняет момент. Это явно описанное предложение, подлежащее проверке на понятность.
- При DST несуществующее локальное время блокирует сохранение с ошибкой у поля; повторяющийся час требует выбора конкретного UTC-смещения. Молчаливого сдвига на час быть не должно.
- Событие через полночь делится на связанные визуальные сегменты по дням отображаемой зоны. Каждый сегмент открывает один и тот же `id`; начало/продолжение различимы текстом или доступной подписью.
- Пересекающиеся события располагаются рядом. Если ширины для них не хватает, доступный `+N events` открывает полный список этого интервала; ни одно событие не теряется. Ограничение числа колонок — решение после визуальной проверки, а не произвольная константа в спецификации.

## 7. Взаимодействия и состояния

| Действие/состояние | Ожидаемый результат |
| --- | --- |
| New event / свободный слот / слот с клавиатуры | Один и тот же редактор, корректно заполненные дата и время. Нажатие существующего события никогда не создаёт новое. |
| Свободная ячейка All day / Enter на ней | Тот же редактор с выбранной датой и включённым All day; одинаково в Day и Week. |
| Create / Save changes | Проверка обязательных полей и диапазона; локальное изменение видно во всех представлениях; редактор закрывается, фокус возвращается в календарь. |
| Cancel / Escape / клик вне формы | Без изменений — закрыть; с изменённым черновиком — запрос Discard changes / Keep editing. Данные не сохраняются до подтверждённого Save. |
| Просмотр → Edit | Та же сущность, полная форма с существующими значениями. Закрытие деталей возвращает фокус на исходное событие. |
| Delete (предложено) | Подтверждение; удаляется только локальная запись, выбранное событие сбрасывается. Возврат фокуса на ближайшую доступную строку или панель. |
| Day ↔ Week ↔ Agenda / density / тема | Выбор события и правки не теряются; открытый черновик не закрывается от изменения темы/размера. |
| Пустой диапазон | No events + New event при разрешённом создании; навигация по датам продолжает работать. |
| Read-only | События доступны для просмотра; управление изменением отсутствует. Это входная настройка демонстрации, не проверка серверных прав. |
| Loading / error | Состояния каталога: недвусмысленный индикатор загрузки или ошибка с повтором; не маскировать ошибку пустым календарём. |
| Ошибка сохранения у будущего адаптера | Черновик сохраняется; ошибка в редакторе, можно повторить или отменить. В синтетическом примере возможна только явно выбранная симуляция. |
| Back/Forward | Восстановление диапазона, вида, выбранного события и прокрутки; несохранённый черновик защищён тем же правилом отмены. |

Жизненный цикл редактора: modal Dialog, без отдельного history entry для каждого поля или открытия формы. Выбор события и смена диапазона — навигация; черновик — локальное состояние. При Back/Forward с изменённым черновиком слой навигации должен удержать текущий контекст до решения Discard / Keep editing; конкретный механизм проверяется в браузере, одного обработчика popstate для такого обещания недостаточно.

URL Showcase позже кодирует страницу, дату, вид, плотность и выбранный `id`; текст описания и черновик в URL не попадают. Удалённый/неизвестный `id` показывает Event unavailable с выходом в текущий календарь. Созданные в памяти события не обещают сохранности после перезагрузки: это ограничение должно быть указано рядом с демонстрацией.

Клавиатура: Tab — панель/сетка/события; стрелки перемещают активный слот в сетке, Enter открывает создание, Enter/Space открывают выбранное событие. Сетка использует управляемый фокус, не сотни Tab-остановок. Dialog/Sheet удерживают и возвращают фокус средствами FrontX/Base UI. Название и полное время доступны без hover. Цвет не единственный признак выбора или типа события.

## 8. Примитивы, токены и темы

Проверенный checkout: `apps/frontx-showcase`, HEAD `67605262247b8ca418139f4aaccdd9fff1101d12`, чистый до добавления этой документации. Это точная база исследования; отдельное новое одобрение визуального baseline не заявляется. Установлен `@gears-frontx/ui-kit@0.4.0-alpha.5`, React 19.2.8. Зависимости не обновлялись.

По умолчанию события имеют нейтральную поверхность и цвет темы только в акценте/выборе. Палитра графиков не превращается автоматически в обязательную радугу календарей. Предметные цвета можно добавить позже как необязательный параметр, с текстовой подписью и проверкой контраста.

Состояния нового EventItem (обычное, hover, selected, focus, read-only) должны жить в одном модуле композиции. Новые страницы не рисуют собственные варианты Button/Input. Отдельной истории event scheduler в проверенных примерах нет: это пробел для следующего шага. В будущем страница Calendar показывает одну и ту же реализацию в разных состояниях, не набор независимо сверстанных макетов.

Сейчас в `src/main.tsx` шесть верхних пунктов: Widgets, Compositions, Modularity, Elements, Colors, Developers. Предложение — **три верхних раздела**, внутренние ссылки на одной площадке:

| Верхний раздел | Внутри |
| --- | --- |
| Components | Calendar · Charts & widgets · Elements |
| Examples | Compositions · Sizing & density (нынешний Modularity) |
| Foundations | Themes (нынешний Colors) · Developer handoff |

Точка входа Calendar — `Components → Calendar`, с примерами Day, Week, Compact agenda и состояниями формы. Старые query-ссылки gallery/widget/layouts/modularity/elements/themes/handoff сохранить и показывать соответствующий активный верхний раздел. Legacy `kind=calendar` по-прежнему относится к Revenue pulse; новый Event Calendar получает самостоятельную страницу, например `page=event-calendar`, без перехвата старых ссылок.

Эта задача предлагает структуру; текущая навигация и публичный сайт не изменены. Размещение на существующем сайте выбрано Денисом как направление, публикация и её дата не утверждены.

## 11. Проверка следующего дизайн-результата

Ниже критерии, а не отчёт о выполненных тестах.

1. Один набор synthetic-событий: Planning, Group work, Course test; последнее — обычное событие, без учебной бизнес-логики.
2. Те же записи и выбранный `id` в Day, Week и Agenda; проверка всех трёх размеров из раздела 4, длинного названия и пяти одновременных событий. Дополнительно: контейнер 280 px с адаптивным Agenda и отдельно принудительный Week с внутренней прокруткой и доступным +N.
3. Создание кнопкой/слотом/клавиатурой → просмотр → изменение → отмена черновика → возврат в список; отдельные события открывают разные данные.
4. All-day на один и несколько дней, 23:30–00:30, пересечение, событие вне рабочих часов, разные зоны и оба случая DST.
5. Все пять тем в light/dark: фон, выбранное событие, поля, контраст текста/фокуса. Проверять реальные состояния, не только token swatches.
6. URL/Back/Forward, неизвестный `id`, смена темы и ширины при открытой форме, перезагрузка локального demo.
7. Keyboard-only, focus return, zoom 200%, узкий контейнер; доступность нельзя подтверждать по статическому изображению.

На ревью с Виталием, Денисом Турановичем и Николой нужно зафиксировать: подходит ли модульная граница, принять ли Agenda и локальное Delete, согласовать ли предлагаемую навигацию, какой реальный экран календаря платформы сравнивать и кто принимает итоговое решение. Это пункты будущего совместного ревью, не повторный опрос Дениса и не основание останавливать текущую спецификацию.
