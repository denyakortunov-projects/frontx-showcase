5 октября 2026. Владелец интеграции — Codex. Исполнитель ограниченных программных частей — существующий Claude Code. Основание: Денис попросил подготовить надёжный план, а затем выполнить его с делегированием и проверкой.

**Текущий результат:** P1–P5 выполнены локально; пользовательское ревью дизайна ожидается. Прямой запуск подтверждён Денисом 5 октября. Публикация не запрошена. Для продолжения использовать этот файл как журнал, а не собирать требования заново из чата.

## 1. Что строим

Переиспользуемый модуль календаря событий внутри **существующего `apps/frontx-showcase`**. Day, Week и Agenda; Standard/Compact; независимые ширина и высота; создание, просмотр, редактирование и локальное удаление с подтверждением. Одни события и один редактор во всех представлениях. Основа — установленный FrontX UI Kit и его темы.

Это локальная демонстрационная композиция для будущих потребителей FrontX, не новый опубликованный экспорт пакета и не готовый календарь платформы. [Дизайн-контракт](DESIGN-2026-10-05.md) содержит подробные правила; этот план управляет выполнением. При расхождении приоритет у новых прямых решений Дениса, затем у дизайн-контракта с явно зарегистрированными поправками.

**Не включаем:** сервер, авторизацию, синхронизацию, настоящие приглашения, RSVP, повторения, вложения, ресурсы/бронирование, drag/resize, месячное расписание, новый сайт или приложение. Не меняем Studio/Fabric, внешние календари, Reminders или встречи. Разработческая интеграция с платформой и её принимающий решение остаются не определены; это не мешает локальному generic-примеру.

### P1 — проверить основу до большого объёма кода

1. Зафиксировать baseline-снимки gallery, widget, elements, themes и навигации. Создать свежую запись из root acceptance template с адаптацией к FrontX: Studio не перестраиваем, его примитивы и IA не переносим.
2. Проверить текущие официальные React API, версию и лицензию нужных модулей FullCalendar. Кандидат из исследования, не предрешённая зависимость. Проверить timezone/DST поддержку и необходимые дополнительные модули, а не обещать её по названию библиотеки.
3. В ограниченном примере проверить: Day/Week, All day, пять пересечений, слот → callback, controlled selection, keyboard entry, token theming, container resize. Использовать FrontX toolbar/editor, а не чужой UI-kit shell.
4. Решение `ENGINE-DECISION.md`: выбрать проверенный движок либо обоснованно перейти к Schedule-X; не оставлять два scheduler-движка в runtime и не писать собственный DST/overlap engine как обходной путь.
5. Зафиксировать `types.ts`: timed vs all-day union, исключающий end, IANA zone; внешние events/date/view/selection; callbacks; представление, плотность, container policy и host capabilities отдельно. Разделить типы композиции и типы выбранного движка.
6. Зафиксировать поведение generic locale/labels, calendar display zone, initial date/clock. Showcase использует английские подписи и воспроизводимые fixtures; Today должен соответствовать явно заданному demo-clock, а не тайно смешивать сегодняшнюю дату с историческими примерами.

**Готово:** движок работает в ограниченном примере, условия использования понятны, размер/zone/keyboard проверены, контракт записан. Если один из пунктов не проходит — не выдавать большую реализацию Claude до исправления решения.

### P2 — первый законченный сценарий

Предполагаемое размещение: `src/calendar/` для модульных композиций, `src/CalendarShowcase.tsx` для обвязки каталога. Не изменять `node_modules`, не копировать примитивы FrontX.

- Claude: типы/fixtures/адаптер, Day и AllDayLane, EventItem, EventDetails, один EventEditor и целевые тесты времени/валидации.
- FrontX: Button, Tabs, Calendar/Popover для даты, Field/Input/Textarea/Checkbox/Select, Sheet, Dialog и AlertDialog. Иконки Lucide.
- Путь: создать кнопкой или timed/all-day слотом → открыть конкретное событие → изменить → сохранить → снова открыть; Cancel оставляет данные прежними.
- Невалидный интервал и пустое название блокируют Save с ошибкой у поля. Отмена грязного черновика запрашивает подтверждение. Локальное удаление подтверждается именем события.
- Codex сразу подключает минимальную страницу `page=event-calendar`, selected event и Back; не откладывает интеграцию состояния до конца.
- Предусмотреть ready/empty/loading/error/read-only в первом пути; сетевые состояния только как явно выбранные синтетические демонстрации.

**Готово:** этот путь работает указателем и клавиатурой в существующем shell, фокус возвращается корректно, Back не теряет черновик или контекст. Тесты + build + небольшой браузерный прогон. Код формы остаётся один.

### P3 — представления и модульность

- Week использует тот же TimeGrid, Agenda — тот же список событий, selection и редактор. При Week → Agenda сохраняется неделя, Day → Agenda — день.
- Плотность не меняет 30-минутный шаг, данные или доступный размер текста. Compact не использует scale или графиковый множитель 65%.
- Контейнеры для проверки: 1120×640, 640×640, 360×360; крайний 280 px. ResizeObserver/контейнерная политика, не только window breakpoint. Forced Week сохраняет локальную горизонтальную прокрутку; auto может перейти в Agenda.
- Отдельный пример двух независимых экземпляров: изменение вида/размера/выбора в одном не меняет второй. Ни query-string, ни local storage не принадлежат generic-компоненту.
- Полный день доступен прокруткой, старт около 08:00; понедельник, видимая зона; выходные и вечер не заблокированы.
- Проверить all-day на несколько дней, timed через полночь, плотные пересечения/+N, короткие события, длинные названия, разные зоны, DST gap/fold.
- Если детальная схема клавиатуры не предоставлена движком, адаптировать её в одном модуле и доказать эквивалентный доступ к слотам и событиям. Не создавать сотни Tab-остановок.

**Готово:** все представления показывают согласованные события, адаптация не теряет данные/выбор/черновик, два экземпляра независимы.

### P4 — единый Showcase

- Три верхних раздела: Components / Examples / Foundations. Calendar внутри Components; список всех графиков вторичен и не заполняет навигацию календаря.
- Сохранить прежние страницы и адреса gallery/widget/layouts/modularity/elements/themes/handoff. Особый regression: `page=widget&widget=calendar` остаётся Revenue pulse.
- Query-поля календаря именовать отдельно от графиков, либо задавать явную маршрутизацию значений: date/view/selected/density/zone/size/fixture. Старые shared width/height/period не должны неожиданно управлять календарём.
- У даты/события/вида есть прямые адреса. Неизвестный id и неверная дата обрабатываются предсказуемо. Черновик и описание события не записываются в URL.
- Back/Forward восстанавливают дату, диапазон, selected event и scroll. Грязный черновик защищён как от кнопок сайта, так и от browser Back. Не считать простую реакцию на popstate доказательством корректной блокировки перехода.
- Локальные edits имеют явно описанный lifecycle: сохранить при смене страниц внутри текущей сессии, сброс при перезагрузке (если не принято иное). Fixtures по прямым адресам воспроизводимы; новые id после reload показывают Event unavailable, а не случайную другую запись.
- Тема и mode используют существующий механизм Showcase. Полноценный пример, compact embed и матрица состояний рендерят один компонент. Developer notes и controls каталога отделены от встраиваемого календаря.

**Готово:** новый компонент доступен через понятную навигацию; старые маршруты, графики и темы не сломаны.
